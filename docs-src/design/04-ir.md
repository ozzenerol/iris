# The IR writer

How `src/ir.c` turns the checked tree into LLVM IR text, and how `src/main.c` hands that text to clang.

## Why text

The IR writer prints LLVM IR as text into a `StrBuf`. Writing text needs no LLVM headers or libraries, so any machine with `clang` can build Iris programs, and the `.ll` file can be read when the output is wrong. `iris ir file.iris` prints it.

## The module it writes

`writeIR(Arena *, Program *, BuildMode)` gathers the declarations of every module into one list, skips generic declarations (only their instances in `Program.instances` are compiled), and writes the module in this order:

1. Named types. `%String = type { ptr, i64, i64 }`, then one type per data enum and one per struct, from `Type.slots` with explicit `[N x i8]` padding. Packed structs use `<{ }>`.
2. The head. `declare` lines for `@extern` C functions (each name once), globals, string constants, method tables for `dyn` and JSON tables.
3. Every function, written by `emitFunction`. Functions of an implicitly loaded `str` module are skipped unless something calls them.
4. The thunks made along the way for `spawn` and `thread` (`IR.extra`).
5. `@main(i32 %argc, ptr %argv)`, which calls `iris_init` and then the program's `main`. A `main` that returns `!void` passes an error to `iris_error_report`. For `iris test` and `iris bench`, `@main` runs each test or bench instead and calls the runtime's summary.
6. `declare` lines for every runtime function the generated code may call: `iris_malloc`, `iris_string_append`, `iris_spawn`, `iris_chan_send`, `iris_error_finish` and the rest.
7. The enum table (`@iris_enum_table`), which the runtime uses to print enum values and error codes by name.
8. Debug metadata.

Names carry their module, so two modules can use the same names:

- `@"f.fs.readAll#0"` is a function. The number after `#` is `Node.inst`, which tells generic instances apart.
- `@"m.main.Point#0.length#0"` is a method.
- `@"g.main.count"` is a global.
- `@"vt.main.File#0.io.Writer"` is a method table.
- `@extern` and `@export` functions keep their C name.

## Functions

`emitFunction` writes one function. It keeps two buffers. `IR.allocas` holds the entry block, with one `alloca` stack slot for every variable and parameter. `IR.body` holds the code. clang's optimizer turns the slots into registers. Values are numbered `%t1`, `%t2`... and labels `L1`, `L2`...

Every function is `nounwind`, since nothing in Iris unwinds the stack. A function that returns `T` returns `llType(T)` (see [How values are stored](05-values.html)). A `void` function given where a `!void` function value is expected gets a small wrapper that returns `i64 0`.

An expression is read as a value by `emitExpr`, which returns a `Val` (an operand string and its `Type`). An expression that names a place in memory is read as an address by `emitAddr`. Assignments, `&` and method receivers use addresses. `emitPlace`, `placeLoad` and `placeStore` handle bitfields and big-endian fields, which need masks and byte swaps.

Statements go through `emitStmt`. `if` and `match` that give a value write into a slot (`emitValueBlock`). `match` becomes comparisons and branches. `for` over a range, a slice, an array or any struct with `next(i64 *at)` is written by `emitFor`.

## defer, errdefer and scoped

There is no lowering pass. The IR writer keeps a stack of `DeferFrame`s, one per block. `defer` and `errdefer` statements and `scoped` variables are pushed on the current frame. At every way out of a block, `runDefers` writes the frames' statements out again, last first: the block's end, `return`, `break`, `continue`, and a `try` that fails. `errdefer` statements are written only on the error paths. A `scoped` variable writes its `free` call: `iris_string_free` for a `String`, `iris_chan_free` for a channel, `iris_json_free` for a `@json` struct without its own `free`, or the type's `free` method.

When deferred code may itself make or handle errors (`touchesErrors` follows calls to find out), the error that is leaving is saved with `iris_error_keep` and restored with `iris_error_back`, so its message and trace survive.

## Errors

`!T` is `{ T, i64 }` in IR, and `!void` is a bare `i64`. The `i64` is the `Error`: zero means no error.

- `error(code, "text")` calls `iris_error_begin`, writes the text into the runtime's next-message buffer, and calls `iris_error_finish(code, file, line, col, fn)`, which makes it the current error and starts its trace.
- `try f()` (`emitTry`) extracts the error, compares it with zero, and branches to a failure block marked unlikely (`!prof !0`). That block calls `iris_trace_add` with the current place, runs the defers and returns the error. When nothing fails, the cost is one comparison.
- `catch` (`emitCatch`) branches the same way into its block or fallback value. A catch block keeps its own copy of the message (`iris_error_save` and `iris_error_restore`), so code inside it can make and handle errors without changing `e.message`.

## Temporary Strings

Text with values passed to a `str` parameter (`F_TEMPTEXT`) is built into a `String` slot, and a `String` returned by a call and passed as a `str` (`F_TEMPSTR`) is kept in one. `addTemp` records the slot, and `freeTemps` calls `iris_string_free` on each when the statement ends, or before any exit from it.

Text with values given to `print` is not built at all. `emitText` writes each part straight to the output buffer with `iris_write_str`, `iris_write_i64` and the other writers.

## spawn and thread

`emitSpawn` stores the call's arguments in a struct allocated with `iris_calloc` and writes a thunk, `@"spawn.N"(ptr %env)`, that loads them, makes the call and frees the struct. `spawn` passes the thunk and the struct to `iris_spawn`. `thread` passes them to `iris_thread_new` and keeps the returned handle as the `Thread`.

`select` (`emitSelect`) builds arrays of the channels and of where each value goes, calls `iris_select` with the timeout of its `after` arm, and switches on the index it returns.

## Checks

In debug builds the IR writer adds a check before every operation that can go wrong:

- `+`, `-` and `*` that overflow, through LLVM's `with.overflow` intrinsics (`emitArith`).
- Division by zero (`emitDivide`).
- Shifts by at least the width of the type (`emitShift`).
- Conversions that lose a value (`emitConvert`).
- Null pointers (`nullCheck`).

Index and slice bounds (`indexCheck`) are checked in debug and release-safe builds. A failed check calls `iris_check_failed`, `iris_index_failed` or `iris_slice_failed`, which print `panic:`, the message and the place, and exit with status 2. Release-safe builds also keep the division checks.

Release-fast builds keep only the index checks of fixed-size arrays. Those checks bound the loops over the arrays, so LLVM can unroll the loops and then remove most of the checks. Unsigned arithmetic wraps around, and signed `+`, `-` and `*` are marked `nsw`, since a debug build would have stopped on an overflow. The step of a `for` over a range is always `nsw` or `nuw`, since the counter is below the end before the step. `@unchecked` drops the checks in one function.

Debug builds also give every function the `sanitize_address` attribute (`attributes #0`). With `-fsanitize=address` that catches use after free and other bad memory accesses. Leak reports are off.

## Allocation

An `alloc` whose count is known calls `iris_malloc` and `memset` directly, so LLVM sees the allocation. One of at most 4 KiB of numbers or pointers that is freed by a `defer` in the same block, and is only indexed, looped over or measured, lives in the function's frame instead (`markStackAlloc`, flag `F_STACK`).

## JSON, @env and @flags

`@json` types get a table the runtime works from: `{ i32 kind, i32 size, i64 count, ptr items }`. A struct's items are its fields, `{ ptr name, i64 nameLen, i64 offset, ptr type, i64 required }`, with embedded structs' fields in line. A slice, array or `List` points at its element's table, and an enum at its values' names. `jsonType` writes the tables and `emitJson` calls `iris_json_encode`, the decoder and `iris_json_free` with them. `@env` and `@flags` structs get similar tables (`envTable`, `flagsTable`), read by `env.load` and `flags.parse` in the runtime. One piece of C serves every type.

## Debug information

The IR writer adds DWARF metadata as it goes. The program gets a compile unit (`!10`). Each source file gets a `DIFile` (`dbgFile`), each function a `DISubprogram`, and every instruction a `!DILocation` with the line and column of the statement or expression it comes from (`dbgAt`). Each named variable and parameter gets a `DILocalVariable` and an `llvm.dbg.declare` on its stack slot, with a debug type from `dbgType`: basic types, pointers, structs with their fields, slices and `String` as structs, arrays and plain enums. All variables share the function's scope, which works because a name can't hide another one in the same function. clang turns this into DWARF with `-g`, which every build passes.

## Calling clang

`compileIR` in `src/main.c` writes `program.ll` and the runtime's source, `rt.c`, into a temporary folder and runs clang (`IRIS_CC` picks another compiler) on both:

1. Debug builds use `-O0 -fsanitize=address`. Both release modes use `-O3 -flto`, so clang optimizes the program and the runtime as one module when it links, and runtime functions such as `iris_string_append`, `iris_malloc` and the channel operations are inlined into the program.
2. Release builds also pass `-falign-loops=32`, and the same to the linker's code generator, so a small hot loop doesn't straddle two 32-byte blocks by chance, which can cost a fifth of its speed.
3. `--cpu` adds `-march` on x86_64 or `-mcpu` on arm64. `--pgo-gen` and `--pgo` add `-fprofile-generate` and `-fprofile-use`, after merging `.profraw` files with `llvm-profdata`. `--target` adds `-target` and `IRIS_SYSROOT`.
4. Every build passes `-g`, the libraries from `link` lines and `-l` options, the project's `.c` files, `-lm` and `-pthread`, and `-ldl` on Linux, since TLS and compression load their libraries when first used.
5. If linking fails, it tries once more: debug builds without AddressSanitizer, whose libraries not every clang has, and release builds without LTO.

The compiled runtime is cached. `cachedRuntime` compiles `rt.c` once per set of flags into `~/.cache/iris/rt/<version>-<hash>.o` (or `$IRIS_PATH/rt`) and reuses it, so a build only compiles the program's own code. The file is written under a temporary name and renamed, so builds running at once never see half a file. PGO builds and `IRIS_NO_RT_CACHE` compile the runtime each time.

`iris run` starts the program from the temporary folder and removes the folder as soon as the program has started, so a program that is killed leaves nothing behind.
